# Phase 0 Audit — HarvestLink (GrapeExchange)

Prepared per `SCOPE_ADDENDUM_NDA_USERNAME_VINEYARD_BULK_WINE.md` Section 2, before any implementation work begins.

---

## 2.1 Stack & conventions

- **Framework**: Next.js 15.5.25, App Router, React 19, TypeScript 5, Tailwind CSS 4. (`package.json`)
- **ORM**: none. Raw `@supabase/supabase-js` via `@supabase/ssr` — Server Components and Server Actions query Postgres directly through the Supabase client. No Prisma/Drizzle/Kysely.
- **DB engine**: Postgres (Supabase-hosted).
- **Migration tool**: none automated. Two hand-written SQL files (`supabase/migrations/0001_init.sql`, `0002_buyer_profile_fields.sql`) that the README says to paste into the Supabase SQL Editor manually. No `supabase/config.toml`, no Supabase CLI wiring, no seed scripts.
- **Test framework**: none. No test script in `package.json`, no jest/vitest/playwright/cypress dependency, zero `*.test.ts`/`*.spec.ts` files under `src`.
- **CI**: none. No `.github/workflows` directory exists.
- **Hosting/CDN**: not configured. README explicitly says Vercel deployment is "not included." No `vercel.json`.
- **Search engine**: none. "Search" is server-rendered Supabase `.eq()/.gte()/.lte()` filtering in `src/lib/data/listings.ts`, state synced to the URL query string. No Algolia/Meilisearch/Typesense/ElasticSearch.
- **Email provider**: none. No Resend/SendGrid/Postmark/nodemailer in dependencies or code. Any auth emails (confirmation/reset) would come only from Supabase Auth's own built-in mailer if enabled at the project level — nothing in the app code sends or customizes email.
- **Image storage**: not actually wired up. `next.config.ts` has a `remotePatterns` entry for `*.supabase.co/storage/v1/object/public/**` (scaffolded, unused). No `supabase.storage.*` call exists anywhere in `src` (confirmed by grep). No image/photo column on `listings`. Cards/detail pages render a static gradient + icon placeholder instead of a real photo (`src/components/marketplace/ListingCard.tsx:20-21`, `src/app/(marketing)/listings/[id]/page.tsx:45-46`).
- **Forms/validation**: `react-hook-form` + `@hookform/resolvers/zod`, with Zod schemas in `src/lib/validation/*.ts` as the single source of truth — used client-side via `zodResolver` and re-run server-side inside `"use server"` actions via `schema.safeParse()`. No separate DTO/serializer layer.
- **API serialization**: there are **no traditional API routes** — `src/app/api` does not exist. Every read is a Server Component calling `src/lib/data/listings.ts` (which calls `createClient()` from `src/lib/supabase/server.ts`, using the anon key, and does `select("*", ...)`). Every write is a colocated `actions.ts` Server Action that client components call like an RPC. There is no central request/response boundary to hang a serializer off of by convention alone.

## 2.2 Auth & users

- **Signup**: `src/app/(auth)/register/page.tsx` (client form) → `src/app/(auth)/register/actions.ts` `handleSignUp()` → `supabase.auth.signUp({ email, password, options: { data: {...} } })`. Role is `grower` or `buyer` (radio buttons); growers require `companyName` + `regionAva`, buyers require `fullName` + `address` (cross-field rules in `src/lib/validation/auth.ts:16-48`, `superRefine`). **No username field anywhere.**
- **Login**: `src/app/(auth)/login/page.tsx` → `actions.ts` `handleSignIn()` → `supabase.auth.signInWithPassword({ email, password })`. Email only — no "login with username" option. Errors are whatever `error.message` Supabase returns, passed straight through (not a custom generic message).
- **User/profile table**: `public.profiles` (`supabase/migrations/0001_init.sql:15-25`, patched in `0002`). Columns: `id` (PK/FK to `auth.users`), `updated_at`, `full_name`, `company_name`, `contact_phone`, `role` (enum: `grower`|`buyer`|`admin`), `region_ava`, `address`, `is_verified`. **No `username`, `display_name`, or `avatar_url` column.** Row auto-created via `handle_new_user()` trigger reading `auth.users.raw_user_meta_data`.
- **Password hashing**: fully delegated to Supabase Auth (GoTrue) — no custom hashing code in this repo at all. App-level password rule is only `z.string().min(8)` (`src/lib/validation/auth.ts:6`) — no max length guidance, no breach-list check, no passphrase messaging.
- **Email verification / password reset**: no dedicated pages/callback routes exist in the Next.js app (no `/verify`, `/reset-password`, `/auth/callback`). Whatever Supabase project-level toggles are set apply server-side, but there is zero app code to drive a reset flow or handle an email-confirmation redirect.
- **Session handling**: cookie-based via `@supabase/ssr` (`src/lib/supabase/client.ts`, `server.ts`), refreshed in `src/middleware.ts` → `src/lib/supabase/middleware.ts` `updateSession()`. Protected prefixes: `/dashboard`, `/listings/create`, `/listings/mine`, `/planning`, plus `/listings/[id]/edit` via regex (`middleware.ts:4-5`). Unauthenticated users are redirected to `/login?redirect_to=...`.
- **Rate limiting**: none found anywhere (no library, no Upstash/KV, no in-memory limiter) — not on login, not on signup, not anywhere.
- **Username/display-name/business-name & public seller identity today**: no username field exists in schema or types at all. The public identity a buyer sees today is `profiles.company_name` (falling back to the string `"HarvestLink Grower"`) on the card (`ListingCard.tsx:35`) and on the detail page's "Listed By" panel (`listings/[id]/page.tsx:99-103`), plus `profiles.region_ava` and an `is_verified` badge. Nothing else from `profiles` is rendered by app code today — **but see Flag #1 below: RLS makes every profiles column readable regardless of what the UI chooses to render.**

## 2.3 Listings

- **Schema** (`public.listings`, `0001_init.sql:30-52`): `id` (uuid PK), `user_id` (FK→profiles), `title` (text, server-generated — see below), `variety` (text), `clone` (text?), `rootstock` (text?), `region_ava` (text, required), `sub_ava` (text?), `estimated_tons numeric(10,2)`, `minimum_tons numeric(10,2)` default 1.00, `price_per_ton numeric(10,2)`, `brix_target numeric(4,1)?`, `description text?`, `status` (`listing_status` enum), `farming_practice` (`farming_practice` enum, default `conventional`), `trellis_system text?`, `soil_type text?`, `sun_exposure text?`, `slope_percent numeric(5,2)?`, `harvest_year integer`, `created_at timestamptz`.
- **Units**: confirmed **tons / price-per-ton** (`estimated_tons`, `minimum_tons`, `price_per_ton`) — matches the spec's assumption exactly. There is no explicit unit column; "tons"/"per ton" is hardcoded in UI strings (`formatTons()` in `src/lib/utils.ts`, literal `" / ton"` suffixes in card/detail components).
- **Statuses**: `available | pending | sold | archived` (`0001_init.sql:10`) — **not** the spec's guessed draft/active/sold/expired. There is no `draft` status; new listings are always inserted as `"available"` server-side (`listings/create/actions.ts:30`). **No expiry/renewal logic exists at all** — no `expires_at` column, no cron/scheduled job.
- **Vineyard field**: **does not exist.** No `vineyard_name`, `single_vineyard`, or equivalent anywhere. Requirement 3 is fully greenfield.
- **Farming-practice field**: **already exists** on `listings` as the `farming_practice` enum with exactly 4 values: `conventional | sustainable | organic | biodynamic` (`0001_init.sql:12`; `src/types/index.ts:4`; `src/lib/constants/viticulture.ts:401-406`, single-select). This differs materially from the spec's bulk-wine set (Organic, Biodynamic, Natural, Sustainable, Regenerative Organic, Demeter Certified Biodynamic — 6 values, multi-select) — see Flag #4.
- **Varietal**: `variety` is a free-text DB column (no CHECK/FK), but the UI restricts input to a large hardcoded list via `<select>` (`GRAPE_VARIETIES_BY_COLOR` in `viticulture.ts`, ~90 names, rendered via `SelectOptionGroups.tsx`). Not a DB lookup table.
- **Appellation/AVA/region**: `region_ava` (required) + `sub_ava` (optional), same pattern — free-text columns, UI-constrained by a hardcoded `AVA_REGIONS` constant (`viticulture.ts:21-256`, ~140 AVAs across CA/WA/OR/NY with state grouping and nested sub-AVAs), not a DB lookup/FK.
- **Location**: listings have no lat/lng/geocoded location; "location" = `region_ava`/`sub_ava` only. A real address-autocomplete field (`src/components/shared/AddressAutocomplete.tsx`, Google Places with a Nominatim/OSM fallback) exists but only for **buyer profiles**, unrelated to listings.
- **Listing URL/slug**: `/listings/[id]` — the raw UUID, **no slug generation exists** (`ListingCard.tsx:17`; `src/app/(marketing)/listings/[id]/page.tsx`).
- **Title generation**: the listing `title` is **auto-generated server-side**, never user-typed — `generateListingTitle(variety, clone, subAva||regionAva)` in `src/lib/utils.ts:20-29`, called from both the create and edit Server Actions. Format: `"{Variety} ({Clone}) — {Region}"`. Only `description` is genuinely seller-authored free text today.

## 2.4 Seller-identity surfaces (every place seller/vineyard identity appears)

- **Cards/detail pages**: `ListingCard.tsx` shows `listing.profiles?.company_name` (line 35, falls back to "HarvestLink Grower") and an `is_verified` badge. Detail page's "Listed By" panel shows `company_name` + `region_ava` + verified badge (`listings/[id]/page.tsx:99-103`, `64-68`). CTA is "Sign In to Contact Grower" → `/login` (no real contact mechanism — see below).
- **"Serializer"/data layer**: `src/lib/data/listings.ts` `getListings()`/`getListingById()` is the closest thing to a public serializer, and it is **not allowlist-based** — `.select("*, profiles(company_name, region_ava, is_verified)")` returns every listing column plus a fixed 3-column profile slice, with no redaction layer. There is no central DTO NDA-4 could hook into today; it must be built new.
- **Critical pre-existing leak vector — RLS**: `profiles` RLS policy is `for select using (true)` with **no column restriction** (`0001_init.sql:108`). Postgres RLS is row-level, not column-level, so the anon key can `SELECT` **any** column of **any** profile — including `contact_phone` and `address` — regardless of what the app's own queries happen to request. This must be closed (column-level security, a view, or a service-role-only data layer) before an NDA-safe serializer can be trusted; picking fewer columns in app code is not sufficient by itself.
- **Seller internal ID exposure**: `listing.user_id` is included in every row returned by `select("*")` in `getListings`/`getListingById` and therefore present in Server Component props / RSC hydration payload for every public listing view today, even though no UI currently renders it — directly the vector NDA-4/NDA-5 forbid.
- **Search/autocomplete/"similar"/"more from this seller"**: none exist anywhere.
- **URLs/slugs/sitemap/RSS/canonical**: no slugs, no `sitemap.ts`, no `robots.ts`, no feed route, no canonical tags anywhere (confirmed via grep for `generateMetadata|sitemap|robots|canonical`).
- **`<title>`/meta/OG/Twitter/JSON-LD**: only one static `metadata` export exists, site-wide, in `src/app/layout.tsx:15-19`. No `generateMetadata` anywhere in the app (confirmed by grep) — listing detail pages currently have **zero** per-listing title/meta/OG/Twitter tags and **zero** structured data. Greenfield: nothing to leak today, but also nothing to reuse.
- **Image upload pipeline**: does not exist (no columns, no upload UI, no `supabase.storage.*` calls anywhere, confirmed by grep). EXIF/filename/alt-text handling is entirely N/A today — good news for NDA-5 (nothing legacy to retrofit), but the whole pipeline must be designed from scratch, NDA-aware from day one.
- **Emails/notifications**: no transactional email system exists at all — no provider, no notification tables, no From-name/reply-to logic. The only "notification" today is a **client-side** Supabase Realtime toast (`useRealtimeListings.ts` / `RealtimeAlertBanner.tsx`) subscribed to `postgres_changes` INSERT events on the whole `listings` table, showing `"New Yield Alert: {tons} of {variety} just listed in {region}"`. It currently only reads 3 safe fields from the payload, but **the full row is broadcast to every subscribed browser** regardless — this channel bypasses any future server-side serializer entirely and must be explicitly revisited for NDA-8/NDA-5 once more sensitive columns exist on `listings`.
- **Buyer↔seller contact**: does **not** exist. The "Sign In to Contact Grower" button is a dead-end link to `/login` — no form, no messaging table, no email reveal. Per NDA-7's own instruction, this is a scope-expansion flag: the minimum relay must be built entirely from scratch.
- **Favorites/saved searches/alerts/share links/print/CSV/PDF export**: none exist (confirmed via targeted search).
- **Admin screens**: none exist. The `user_role` enum includes `'admin'` (`0001_init.sql:9`) but it is never referenced anywhere else in the codebase — no admin routes, no role-gating (not even in middleware, which only checks "is logged in," never role), no moderation UI.
- **Analytics/logging/error reporting**: none found — no Sentry/PostHog/Segment/GA/Vercel Analytics anywhere.
- **Caching**: no CDN/page-cache/search-cache layer. Only Next.js's own `revalidatePath()` calls after create/update (`listings/create/actions.ts:35-36`, `listings/[id]/edit/actions.ts:44-47`). No custom cache headers, no ISR config, no `vercel.json`.

## Surprises / Flags

1. **`profiles` RLS leaks every column to anonymous reads.** `for select using (true)` (`0001_init.sql:108`) has no column restriction, so `contact_phone`/`address` are technically fetchable by anyone with the anon key today, regardless of what the app UI chooses to render. This is the single biggest structural issue for building a trustworthy NDA-4 "allowlist" serializer — the allowlist has to be enforced at/below the DB layer, not just by writing fewer `.select()` columns in app code.
2. **`listing.user_id` (seller's internal ID) is already present in every public listing payload** via `select("*")` in `src/lib/data/listings.ts`, i.e., already in the RSC hydration payload for every listing view — exactly what NDA-4/NDA-5 say public responses must never include.
3. **Listing titles are already server-generated**, never seller-typed (`generateListingTitle()`), so only `description` is genuinely free text today for the NDA-6 guard on grapes listings — worth confirming with the project owner whether NDA-6's title-scanning requirement still applies to an auto-generated title once bulk wine (presumably titled the same way) exists.
4. **Existing `farming_practice` enum (4 single-select values) ≠ spec's bulk-wine farming-practices list (6 multi-select values).** They're also structurally different (single enum column vs. multi-select join table). Per the spec's own Open Question #6, grapes stays untouched unless approved — so two parallel vocabularies will coexist unless the project owner signs off on unifying them.
5. **No `draft` status exists** (statuses are `available/pending/sold/archived`) — Section 7.4's "autosave drafts" has no existing draft concept to build on.
6. **Listing URLs are raw UUIDs**, not slugs — `WINE-2`'s `/grapes/{slug}-{id}` pattern and its 301-redirect requirement are both fully greenfield; there's no existing slug generator or "pretty URL" to preserve beyond `/listings/{id}` itself.
7. **There are zero API routes.** Everything is direct-to-Supabase Server Components/Actions. A "central public-listing serializer" (NDA-4) has no natural single choke point to sit behind (no gateway/route layer) — it will have to be enforced by convention (a shared function every listing-reading Server Component/Action must call), which is inherently easier to bypass by accident than a route-level boundary. Flag this explicitly for the NDA-4 design phase.
8. **Supabase Realtime broadcasts the full `listings` row to every subscribed browser tab** on INSERT (`useRealtimeListings.ts`), independent of any server-side serializer. It only reads 3 safe fields today, but the underlying payload is unfiltered — this channel needs its own NDA-aware treatment (filtered publication, narrower broadcast columns, or an authenticated/foreign-key-scoped channel) once more sensitive columns land on `listings`.
9. **No rate limiting exists anywhere** — USR-1 (rate-limited availability check) and USR-6 (login rate limiting/lockout) both require net-new infrastructure.
10. **No test framework and no CI exist** — Section 8's mandatory canary test needs both a test runner and a CI pipeline stood up from scratch, not just a new test file.
11. **No image upload pipeline exists at all** — actually favorable for NDA-5 (no legacy leaking images to fix), but means the entire pipeline (storage, EXIF stripping, random filenames, alt text) is 100% new work, ideally NDA-aware from the first commit rather than retrofitted.
12. **`role` enum already has `'admin'` but zero admin infrastructure** (no routes, no guards, no UI) — a natural hook for NDA-11 but nothing to build on yet.
13. **"Contact grower" is a dead link today** (`/login`), confirming NDA-7's audit question: there is no existing inquiry/messaging system. Per the spec's own instruction, this should be flagged to the project owner as a scope expansion before building beyond the minimum relay.
14. **Varietal/AVA/farming-practice/trellis/soil/sun-exposure are UI-only controlled** (hardcoded TS constants driving `<select>`s) — the DB columns themselves are plain `text` with no CHECK/FK constraints. VIN-3 wants these "controlled" going forward; today that control exists only in the UI layer, not the database, for any of the existing grape fields either.
15. `.env.example` documents Stripe vars as "Future Scope for Premium Listings/Verifications" — confirms no payment processing exists yet (not in scope for this addendum, but worth knowing).
